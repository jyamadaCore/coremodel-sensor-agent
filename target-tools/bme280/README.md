# target-tools/bme280

Two separate pieces, on two separate machines:

```text
  host/    -> builds & runs on YOUR MAC (the sensor/model side)
  target/  -> cross-compiled & runs ON THE IMX93 (the I2C master side)
```

```text
  [ host/bme280_coremodel_inject ]  <--- network: 10.11.1.11:1900 --->  [ CoreModel VM ]
          (your Mac — the BME280 model, w/ synthetic calibration)                 |
                                                                         virtual lpi2c1 bus
                                                                                    |
                                                                [ imx93evk Linux, /dev/i2c-N ]
                                                                [ target/bme280_i2c_tool ]
                                                                (the imx93 — the I2C master)
```

Both pieces are hand-written tooling for real/virtual hardware, not output
of the sensor-model-builder agent — kept out of `sensor-models/bme280/`
since that directory is reserved for the agent's generated files. Never
build or copy `host/` onto the imx93, and never try to cross-compile or
run `target/bme280_i2c_tool` on your Mac.

## `host/` — runs on your Mac

The CoreModel model at `sensor-models/bme280/` (7-bit address `0x76`,
generated by this agent) already exists for exactly this: testing against
a virtual LPI2C bus before wiring up a real sensor. But the bare
`sensor-models/bme280/bme280-coremodel` binary leaves calibration at the
documented placeholder of all-zero bytes, and raw pressure/temperature at
`0x80000`/humidity at `0x8000`
([sensor-models/bme280/README.md](../../sensor-models/bme280/README.md)).
Since every BME280 compensation formula multiplies by its calibration
coefficients, all-zero calibration forces every compensated reading to
`0.00` regardless of the raw ADC data — by design, but useless for
exercising `target/bme280_i2c_tool`'s real compensation math.

`bme280_coremodel_inject` is that same model, but with a self-consistent
*synthetic* (not from any real chip) calibration table and raw ADC
reading loaded via `bme280_set_calibration_byte()` /
`bme280_set_raw_temperature()` / `bme280_set_raw_pressure()` /
`bme280_set_raw_humidity()` before it attaches to CoreModel. It compensates
to approximately `T=25.1 C`, `P=1006.5 hPa`, `H=21.3 %RH`. This relies on
`bme280_model.c`'s `complete_forced_measurement()` only resetting
pressure/temperature/humidity to the power-on placeholder when that
measurement's oversampling is disabled — `target/bme280_i2c_tool` always
requests oversampling x1 on all three, so the injected values survive its
forced-mode trigger untouched.

`bme280_model.{c,h}` here are vendored copies of
`sensor-models/bme280/src/{bme280_model.c,bme280_model.h}`, and
`coremodel.{c,h}` are vendored copies of
`target-tools/example-spi-dac-actuator/host/coremodel.{c,h}`, so `host/`
builds standalone. Re-copy `bme280_model.{c,h}` here if the agent
regenerates that model.

Build and run, on your Mac:

```sh
cd host
make
./bme280_coremodel_inject 10.11.1.11:1900 lpi2c1
```

Stop any other `bme280-coremodel`/`bme280_coremodel_inject` already
attached to the same bus/address first — only one process can hold a given
I2C address at a time.

## `target/` — cross-compiled for, and runs on, the imx93

`bme280_i2c_tool` is the I2C master: it opens a Linux i2c-dev node
(`/dev/i2c-N`) and talks to a BME280 using the `I2C_RDWR` ioctl, so each
register read is a combined register-address-write-then-data-read
transaction with a repeated start — required for the BME280's
multi-byte status/data/calibration reads to stay consistent. No vendor BSP
libraries are needed, just the kernel's `linux/i2c.h` / `linux/i2c-dev.h`
headers, so it will not build on a machine without Linux kernel headers
(e.g. macOS) — that's expected, matching
`target-tools/example-spi-dac-actuator/target/`.

Temperature/pressure/humidity compensation uses the double-precision
reference formulas from the Bosch BME280 datasheet.

Cross-compile from your host and copy the binary to the imx93:

```sh
cd target
make PREFIX=aarch64-linux-gnu-
scp bme280_i2c_tool root@<imx93>:~/
```

Or build directly on the target if it has `gcc` and kernel headers:

```sh
cd target
make
```

### Finding the right /dev/i2c-N for LPI2C1

Linux's `/dev/i2c-N` nodes are indexed by the order I2C controllers are
enabled in the device tree, which is not guaranteed to match the silicon
instance number in `LPI2C1`. Confirm which node is actually LPI2C1 with:

```sh
cat /sys/class/i2c-dev/i2c-*/name
# or
i2cdetect -l
```

Each line's device-tree node name/register-base address can be matched
against the `&lpi2c1` node in your board's `.dts`/`.dtsi` to find the right
`N`. If nothing shows up under `/dev/i2c-*` at all, LPI2C1 (or `i2c-dev`
itself) is disabled in the devicetree/kernel config.

### Usage, on the imx93

Replace `/dev/i2c-N` with whatever node actually maps to LPI2C1, and `0x76`
with `0x77` if the BME280's SDO pin is tied high instead of low:

```sh
./bme280_i2c_tool /dev/i2c-N 0x76 id
./bme280_i2c_tool /dev/i2c-N 0x76 dump
./bme280_i2c_tool /dev/i2c-N 0x76 once
./bme280_i2c_tool /dev/i2c-N 0x76 stream 2
./bme280_i2c_tool /dev/i2c-N 0x76 read 0xd0
./bme280_i2c_tool /dev/i2c-N 0x76 write 0xf2 0x01
```

`id` should read back `0x60`. `dump` prints the raw chip-ID, calibration,
status, and data bytes in hex — useful for diagnosing bad reads without
the compensation math in the way. `once` triggers a single forced-mode
conversion and prints compensated temperature/pressure/humidity. `stream`
repeats that every `interval_s` seconds (default 1) until you Ctrl+C —
this is the "listen" loop.

### If T/P/H all read as exactly 0.00

This means the calibration bytes (`dig_T1`, `dig_T2`, `dig_T3`, `dig_P1`,
`dig_H2`, ...) are themselves all zero — every compensation formula
multiplies by these, so zero calibration forces zero output no matter what
the raw ADC data is. Run `dump` and check the `CALIB1`/`CALIB2` lines:

- If you're pointed at a virtual bus (`bme280-coremodel`), this is
  expected — see `host/` above and use `bme280_coremodel_inject` instead.
- If you're pointed at real hardware and calibration still reads all
  zero, the chip either hasn't powered up correctly or is a counterfeit
  module with blank calibration OTP — a known issue with cheap/clone
  BME280 boards.

### If a transaction fails with "Invalid argument" or "No such device or address"

- `ENODEV`/`ENXIO` on every register read usually means the address is
  wrong (`0x76` vs `0x77`) or nothing is actually wired to that bus.
- `EINVAL` from `ioctl(I2C_RDWR)` usually means the `/dev/i2c-N` path isn't
  actually an i2c-dev node, or the kernel doesn't have `i2c-dev` loaded —
  check `lsmod | grep i2c_dev` and `ls -l /dev/i2c-*`.
